### Q3：项目中遇到了什么难点？

> 最大的难点是选课的并发问题。比如一门课容量是 40 人，如果有 50 个学生同时点选课，不能让超过 40 个人成功。
>
> 我一开始用的是先查后插的方式，就是先查当前已选人数，没超就插入。但这个方案有并发问题——两个线程可能同时查到当前是 39 人，然后都插入，就超了。后来我改成了 MySQL 的 SELECT FOR UPDATE 行锁，在事务里先锁住课程这一行，再查容量，再插入选课记录，这样就把这个操作变成了原子性的，不会出现并发超选的问题。
>
> 另一个难点是候补队列的自动提升。退课的时候，我不能只是简单地标记退课，还需要把最早进入候补的学生提升为已选。这个操作必须和退课在同一个事务里，如果提升失败，退课也要回滚。我用 @Transactional 注解保证这一点，退课和提升是一个原子操作。
>
> 还有一个比较细节的问题是 SQL 注入。我的学生列表和选课列表都支持动态排序，用户传排序字段和排序方向。如果直接拼 SQL，用户传一个恶意字符串就有注入风险。我用了一个 Map 白名单，只有白名单里的字段名才允许排序，不在白名单里的直接拒绝。

### Q4：微服务是怎么拆的？为什么要拆？

> 我是按业务域来拆的。学生、教师、课程、选课各自是独立的微服务，每个服务有自己的数据库表。这样做的好处是各模块可以独立开发、独立部署，也方便后续独立扩展。坏处是跨服务调用需要处理分布式事务和 Session 共享的问题。

> 我用了 Eureka 做服务注册和发现，Gateway 做统一入口和路由。不过坦白说，目前因为 Session 跨服务共享的问题，Gateway 配置的是把所有请求统一转发到 web-service，微服务的路由暂时注释掉了。如果要真正拆开，需要引入 Redis 来共享 Session，或者改成 JWT 无状态认证。这是我后续计划优化的方向。
>
> 这个事情也让我认识到，微服务拆分不仅仅是代码拆分，还涉及到分布式事务、服务发现、链路追踪、配置中心等一整套基础设施的搭建。

## 第二部分：Java 基础

### Q6：说一下 == 和 equals 的区别

> == 对基本类型比较的是值，对引用类型比较的是内存地址。equals 方法默认也是比较地址，因为 Object 类里的 equals 就是用的 ==。但是像 String、Integer 这些类重写了 equals 方法，改成比较内容了。
>
> 这里有一个重要的点，就是如果重写 equals 方法，就必须同时重写 hashCode 方法。因为 HashMap 和 HashSet 在判断元素是否存在时，会先比较 hashCode，hashCode 相同再比较 equals。如果只重写 equals 不重写 hashCode，可能会导致两个 "相等" 的对象 hashCode 不同，在 HashMap 里就会出问题。

### Q7：HashMap 底层原理？

> JDK 1.8 的 HashMap 底层是数组加链表加红黑树。主体是一个 Node 数组，每个位置是一个链表头。put 的时候先算 hash，hash 是 key 的 hashCode 经过扰动函数处理后的值，然后用 (n-1) & hash 定位数组下标。
>
> 如果这个位置没有元素，直接放进去。如果有元素，就遍历链表，key 相同就覆盖，不同就追加到链表尾部。当链表长度超过 8 且数组长度超过 64 的时候，链表会转成红黑树，这样查询效率从 O(n) 变成 O(log n)。当红黑树节点减少到 6 以下时，会退化回链表。
>
> 扩容方面，初始容量是 16，负载因子 0.75，也就是说元素超过 12 个就会扩容，扩容是翻倍。JDK 1.8 扩容的时候做了优化，只需要看 hash 值的最高位，如果是 0 就留在原位置，是 1 就移到原位置加旧容量的位置，不需要重新计算 hash。

### Q8：HashMap 为什么线程不安全？

> 主要有两个问题。在 JDK 1.7 中，并发扩容的时候可能形成环形链表，导致 get 操作死循环。JDK 1.8 改成了尾插法解决了环的问题，但还是有并发数据覆盖的问题——两个线程同时 put 到同一个桶位置，一个线程的写入可能被另一个覆盖。
>
> 另外 put 和 get 并发的时候，可能 get 到 null 值，因为一个线程在 put 时正好在设置引用，另一个线程 get 就拿到了还没设置完的值。
>
> 如果需要线程安全，可以用 ConcurrentHashMap，也可以用 Collections.synchronizedMap，但推荐用 ConcurrentHashMap。

### Q9：ConcurrentHashMap 怎么保证线程安全？

> JDK 1.7 用的是分段锁 Segment，把整个 Map 分成 16 段，每段一把锁，不同段之间可以并发访问。但并发度只有 16，而且实现比较重。
>
> JDK 1.8 改成了 CAS 加 synchronized 的方式。锁的粒度从段变成了桶，也就是数组的每个位置。put 的时候，先用 CAS 尝试写入，如果桶是空的就 CAS 写入；如果桶有元素，就用 synchronized 锁住链表头或红黑树根，然后在锁内操作。读操作完全不加锁，因为 Node 的 val 和 next 都用 volatile 修饰了，保证了可见性。
>
> 这样设计的好处是并发度大幅提升，而且读操作完全无锁，性能很好。

### Q10：String / StringBuilder / StringBuffer 区别？

> String 是不可变的，因为它的 char 数组用 final 修饰了。每次对 String 做拼接操作，实际上都会创建新的 String 对象，效率低。
>
> StringBuilder 和 StringBuffer 都是可变的，内部维护一个可变的 char 数组，拼接操作直接在原数组上追加。区别是 StringBuffer 是线程安全的，方法都加了 synchronized，但性能差。StringBuilder 没加锁，性能好，但不是线程安全的。
>
> 一般在单线程场景下用 StringBuilder，比如在方法内部拼接字符串。如果是多线程共享的场景，用 StringBuffer。另外编译器对 String 的加号拼接做了优化，会自动转成 StringBuilder.append，所以在循环外面用加号拼接是没问题的，但循环里面还是建议手动用 StringBuilder。

## 第三部分：多线程与并发

### Q11：说一下 synchronized 的原理

> synchronized 是 JVM 层面的锁，锁的是对象。每个对象在对象头里有一个 Mark Word，里面存了锁信息。
>
> 锁有一个升级的过程。一开始是无锁状态。当一个线程第一次获取锁时，会升级为偏向锁，把线程 ID 写入对象头。下次同一个线程再来，只需要比较线程 ID 就行，不需要 CAS。如果有第二个线程来竞争，就升级为轻量级锁，用 CAS 加自旋。如果自旋超过一定次数还没拿到锁，就升级为重量级锁，走操作系统的 mutex 互斥量，线程会被挂起阻塞。
>
> 这个锁升级的设计是为了在不同竞争程度下都能有比较好的性能。竞争不激烈的时候用偏向锁或轻量级锁，开销很小；竞争激烈的时候才用重量级锁。

### Q12：synchronized 和 ReentrantLock 的区别？

> 第一点，synchronized 是 JVM 内置的，加锁和释放锁都是自动的，不需要手动写代码。ReentrantLock 是 API 层面的锁，需要手动 lock 和 unlock，如果忘了 unlock 就会死锁，所以一般在 finally 里释放。
>
> 第二点，synchronized 是非公平锁，ReentrantLock 可以选择公平或非公平。公平锁是先来先得，非公平锁是允许插队。
>
> 第三点，synchronized 不可中断，一个线程在等锁的时候不能被中断。ReentrantLock 可以用 lockInterruptibly 方法实现可中断加锁。
>
> 第四点，synchronized 只有一个等待队列，通过 wait 和 notify 实现。ReentrantLock 可以创建多个 Condition，每个 Condition 有自己的等待队列，可以精确唤醒。
>
> 底层实现也不同，synchronized 是 JVM 层面基于对象头和 Monitor 实现，ReentrantLock 是基于 AQS 实现的。
>
> 如果不需要 ReentrantLock 的高级功能，用 synchronized 就够了，而且 JDK 1.6 之后 synchronized 做了很多优化，性能和 ReentrantLock 差距不大。

### Q13：volatile 的作用？

> volatile 有两个作用。第一是保证可见性，一个线程修改了 volatile 变量，其他线程能立刻看到。这是因为 volatile 变量的读写会直接操作主内存，不会读到 CPU 缓存的旧值。底层是基于 MESI 缓存一致性协议。
>
> 第二个作用是禁止指令重排。编译器和 CPU 为了优化性能会对指令进行重排，但在多线程环境下可能导致问题。volatile 通过插入内存屏障来禁止重排。
>
> 但 volatile 不保证原子性。比如 i++ 操作，实际上是从读、加、写三步，不是原子的。要保证原子性可以用 AtomicInteger 或者 synchronized。
>
> 典型应用场景是双重检查锁的单例模式。new 一个对象其实分三步：分配内存、初始化、把引用赋给变量。如果没有 volatile，2 和 3 可能重排，导致其他线程拿到一个还没初始化的对象。

### Q14：说一下 CAS

> CAS 全称是 Compare And Swap，比较并交换。它是一种乐观锁的思想，操作的时候先比较值是否等于预期值，如果等于就更新，否则不操作。它是原子操作，由 CPU 的 cmpxchg 指令保证。
>
> 在 Java 中，CAS 通过 Unsafe 类的 compareAndSwapInt 等方法实现。AtomicInteger 的 incrementAndGet 就是用 CAS 实现的，底层是自旋，一直尝试直到成功。
>
> CAS 有三个问题。第一是 ABA 问题，一个值从 A 变成 B 再变回 A，CAS 检查不出来。解决方法是加版本号，用 AtomicStampedReference。第二是自旋开销大，如果竞争激烈，一直 CAS 失败会浪费 CPU。第三是只能保证一个变量的原子操作，多个变量需要用 AtomicReference 包装成对象。

### Q15：说一下 AQS

> AQS 全称是 AbstractQueuedSynchronizer，是 JUC 包里大部分同步工具的基础框架。ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 都是基于 AQS 实现的。
>
> 核心是两个东西。一个是 state，一个 volatile int，不同的同步工具赋予不同的语义。在 ReentrantLock 里 state 表示锁被重入了几次，0 是没人锁，1 是锁一次，2 是锁两次。在 Semaphore 里 state 表示剩余的许可数。在 CountDownLatch 里 state 表示还剩多少个计数。
>
> 另一个是 CLH 队列，一个双向链表，存的是获取锁失败后被阻塞的线程。每个节点封装了一个线程引用和一个等待状态。线程尝试获取锁失败后，会被包装成一个 Node 加到队列尾部，然后调用 LockSupport.park 把自己挂起。当锁被释放时，队首的线程会被 unpark 唤醒，它被唤醒后重新尝试 CAS 获取锁。
>
> AQS 有两种模式：独占模式和共享模式。ReentrantLock 是独占的，同一时刻只有一个线程能获取锁。Semaphore 和 CountDownLatch 是共享的，可以有多个线程同时获取。

### Q16：说一下线程池的参数和执行流程

> 线程池有 7 个核心参数。corePoolSize 是核心线程数，maximumPoolSize 是最大线程数，keepAliveTime 是非核心线程的空闲存活时间，unit 是时间单位。这四个控制线程的数量和生命周期。
>
> workQueue 是任务队列，核心线程忙不过来的时候，新任务会先进队列。threadFactory 是线程工厂，用来创建线程。handler 是拒绝策略，队列满了、线程也到最大值了，新任务怎么处理。
>
> 执行流程是这样的：提交一个任务后，先看核心线程有没有满，没满就创建核心线程执行。如果满了，就把任务放到队列里。如果队列也满了，就创建非核心线程，一直到 maximumPoolSize。如果最大线程也满了，就执行拒绝策略。
>
> 拒绝策略有四种。默认是 AbortPolicy，直接抛异常。CallerRunsPolicy 让提交任务的线程自己执行。DiscardPolicy 直接丢弃。DiscardOldestPolicy 丢弃队列里最老的任务，然后重新提交。
>
> 生产环境推荐用 ThreadPoolExecutor 手动创建线程池，不要用 Executors 的快捷方法。因为 newFixedThreadPool 和 newSingleThreadExecutor 用的是无界队列，可能 OOM。newCachedThreadPool 最大线程数是 Integer.MAX_VALUE，也可能创建大量线程导致 OOM。

### Q17：说一下 ThreadLocal

> ThreadLocal 是线程本地变量，每个线程有自己独立的副本，互不干扰。
>
> 原理是这样的。每个 Thread 对象里有一个 ThreadLocalMap，key 是 ThreadLocal 实例，value 是你要存的值。当你调用 threadLocal.set 方法时，实际上是以这个 ThreadLocal 实例为 key，把值存到当前线程的 ThreadLocalMap 里。get 的时候也是从当前线程的 Map 里取。
>
> 这里有一个内存泄漏的问题。ThreadLocalMap 的 key 是弱引用，value 是强引用。当 ThreadLocal 实例没有被外部强引用时，GC 会回收 key，但 value 不会被回收，因为它是强引用。如果线程一直存活（比如线程池里的线程），这些 value 就一直不会被回收，造成内存泄漏。
>
> 解决方法是每次用完 ThreadLocal 后调用 remove 方法，把 key 和 value 都清掉。
>
> 另外在线程池环境下还有一个问题，因为线程会被复用，上一个任务设置的 ThreadLocal 数据会残留到下一个任务。所以用完一定要 remove。阿里有一个 TransmittableThreadLocal 可以解决线程池中 ThreadLocal 传递的问题。

### Q18：死锁的条件和怎么排查？

> 死锁产生需要四个条件同时满足。第一是互斥，资源同一时刻只能被一个线程使用。第二是占有并等待，线程已经持有了至少一个资源，又在等待获取新的资源。第三是不可剥夺，资源不能被强行夺走，只能等持有者主动释放。第四是循环等待，多个线程形成头尾相接的循环等待链。
>
> 排查死锁可以用 jstack 命令，它会输出所有线程的状态和调用栈，并且会直接告诉你检测到了死锁，告诉你哪几个线程互相死锁了。也可以用 jconsole 或 VisualVM 的图形界面来查看。
>
> 预防死锁最常用的方法是破坏循环等待条件，比如规定所有线程按照相同的顺序获取锁，这样就不会形成环。或者使用 tryLock 设置超时时间，如果一段时间内获取不到锁就放弃，释放已经持有的锁。

## 第四部分：JVM

### Q19：说一下 JVM 内存区域

> JVM 内存分为线程私有和线程共享两类。
>
> 线程私有的有三块。第一是虚拟机栈，每个方法调用会创建一个栈帧，存局部变量表、操作数栈、方法出口等信息。方法的调用就是栈帧的入栈和出栈。第二是本地方法栈，和虚拟机栈类似，只不过服务的是 Native 方法。第三是 PC 寄存器，存的是当前线程执行的字节码行号。
>
> 线程共享的也有两块。第一是堆，所有对象实例和数组都在堆上分配，这也是 GC 的主要区域。堆分为新生代和老年代，新生代又分为 Eden 和两个 Survivor 区。第二是方法区，存类信息、常量、静态变量等。JDK 8 之后方法区的实现在元空间，用的是本地内存，不在堆里。
>
> 另外还有一个直接内存，是 NIO 用的，通过 allocateDirect 分配，不受 JVM 堆大小限制。

### Q20：说一下 GC 机制

> 首先是怎么判断对象能不能回收。用的是可达性分析算法，从 GC Roots 出发，沿着引用链向下搜索，如果一个对象到 GC Roots 没有任何引用链相连，就是不可达的，可以被回收。GC Roots 包括栈中引用的对象、静态变量引用的对象、常量引用的对象、JNI 引用的对象。
>
> 回收算法有三种。标记-清除算法，先标记可达对象，然后清除不可达的，缺点是会产生内存碎片。标记-整理算法，标记后把存活对象压缩到一端，没有碎片但慢。复制算法，把存活对象从一块内存复制到另一块，没有碎片且快，但浪费一半空间。
>
> 实际使用的是分代收集策略。新生代用复制算法，因为大部分对象很快就死了，存活率低。每次 GC 把 Eden 和当前 Survivor 的存活对象复制到另一个 Survivor，然后清空。老年代用标记-整理，因为老年代存活率高，不适合复制算法。
>
> 垃圾收集器方面，CMS 是老年代收集器，特点是低延迟，用并发标记清除，但有碎片问题。G1 是全堆收集器，把堆分成很多 Region，每次回收价值最高的 Region，可预测停顿时间。ZGC 是最新的，用染色指针，停顿时间在 10 毫秒以内。

### Q21：说一下类加载过程和双亲委派

> 类加载分为 5 个阶段。加载阶段，通过类的全限定名找到二进制字节流，然后生成 Class 对象。验证阶段，验证字节码的格式、元数据、字节码、符号引用是否合法。准备阶段，为静态变量分配内存并赋默认值，比如 int 赋 0。解析阶段，把符号引用解析成直接引用。初始化阶段，执行类构造器方法，执行静态代码块和静态变量的赋值。
>
> 双亲委派模型是指类加载的时候，先委派给父加载器去加载，父加载器加载不了才自己加载。层级是 BootstrapClassLoader 加载核心类，ExtClassLoader 加载扩展类，AppClassLoader 加载应用类，自定义 ClassLoader 在最下面。
>
> 双亲委派的好处是安全，防止用户自定义一个 java.lang.String 类来替换核心类。因为请求会先委派给 Bootstrap，它已经加载了真正的 String，你的假 String 不会被加载。另一个好处是避免重复加载。
>
> 打破双亲委派的场景，一个是 Tomcat，每个 Web 应用有独立的 ClassLoader，目的是让不同应用可以使用不同版本的同一个类。另一个是 JDBC，Driver 接口在 rt.jar 里由 Bootstrap 加载，但具体实现在 classpath 里，Bootstrap 加载不到，所以用 ContextClassLoader 来加载。

## 第五部分：MySQL

### Q22：MySQL 事务的隔离级别？

> MySQL 有四种隔离级别。READ UNCOMMITTED 读未提交，最低级别，有脏读问题，就是一个事务能读到另一个事务还没提交的数据。READ COMMITTED 读已提交，解决了脏读，但不可重复读，就是同一事务里两次读同一行数据可能不同。REPEATABLE READ 可重复读，解决了不可重复读，但理论上还有幻读问题，就是同一查询两次结果行数不同。SERIALIZABLE 串行化，最高级别，解决所有问题但性能最差。
>
> MySQL 默认是 REPEATABLE READ。InnoDB 在这个级别下，通过 MVCC 解决了快照读的幻读问题，通过 Next-Key Lock 解决了当前读的幻读问题。
>
> MVCC 的原理是每行记录有隐藏的 trx_id 和 roll_pointer 字段。trx_id 是最后修改这条记录的事务 ID，roll_pointer 指向 undo log 中的旧版本。读的时候会生成一个 Read View，包含当前所有活跃事务的 ID 列表。判断一个版本是否可见的方法是：如果 trx_id 小于活跃事务的最小 ID，说明在生成 Read View 之前就提交了，可见。如果大于最大 ID，说明是之后开始的事务，不可见。如果在这个范围内，看是否在活跃列表里，在就不可见，不在就可见。不可见就通过 roll_pointer 找上一个版本继续判断。
>
> RC 级别下每次 SELECT 都会生成新的 Read View，所以能看到其他事务提交的最新数据，导致不可重复读。RR 级别下只在第一次 SELECT 时生成 Read View，后续复用，所以看到的是第一次读时的快照，实现了可重复读。

### Q23：MySQL 索引底层结构？

> InnoDB 的索引底层是 B+ 树。B+ 树的特点是所有数据都存在叶子节点上，非叶子节点只存索引和指针。叶子节点之间通过双向链表连接，支持范围查询。
>
> 相比于 B 树，B+ 树有几个优势。第一，非叶子节点不存数据，所以每个节点能存更多索引项，树更矮，磁盘 IO 次数更少。第二，叶子节点有链表，范围查询只需要找到起点然后沿链表遍历就行，非常高效。第三，所有数据都在叶子节点，查询性能稳定，不会像 B 树那样有的快有的慢。
>
> InnoDB 有两种索引。聚簇索引就是主键索引，叶子节点存的是整行数据。非聚簇索引也叫二级索引，叶子节点存的是主键值。通过二级索引查询时，如果需要的字段不在索引里，就需要回表，就是先从二级索引查到主键，再从聚簇索引查到整行数据。
>
> 如果查询的字段都在索引里，就不需要回表，这叫覆盖索引。可以用 EXPLAIN 查看，Extra 列显示 Using index 就说明用了覆盖索引。

### Q24：什么情况下索引会失效？

> 有好几种情况。第一种是对索引列使用函数或计算，比如 WHERE YEAR(create_time) = 2024，这会导致全表扫描。应该改成 WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01'。
>
> 第二种是类型转换，比如 phone 字段是 varchar，但查询时写 WHERE phone = 13800138000，MySQL 会把字符串转成数字来比较，导致索引失效。应该加引号。
>
> 第三种是 LIKE 的前导模糊查询，LIKE '%abc' 会导致索引失效，因为 B+ 树是按前缀排序的。LIKE 'abc%' 可以用索引。
>
> 第四种是 OR 条件，如果 OR 两边不都有索引，会导致全表扫描。
>
> 第五种是不满足最左前缀原则。比如联合索引 (a, b, c)，查询条件只有 b 或 c，用不到索引。如果有 a 和 b 的范围查询，b 后面的 c 也会失效。
>
> 另外 != 和 NOT IN 也可能导致索引失效，因为优化器可能认为全表扫描更快。是否真的失效要看 EXPLAIN 的结果，MySQL 优化器会根据数据量和成本来决定。

### Q25：MySQL 锁有哪些？

> 从粒度上分，有全局锁、表锁和行锁。全局锁是 FLUSH TABLES WITH READ LOCK，整个数据库只能读不能写。表锁有 LOCK TABLES 和元数据锁 MDL。行锁是 InnoDB 特有的。
>
> 行锁又分几种。记录锁 Record Lock，锁住单行记录。间隙锁 Gap Lock，锁住一个区间但不含记录本身，主要目的是防止幻读。临键锁 Next-Key Lock，是记录锁加间隙锁，锁住一个左开右闭区间，这是 InnoDB 在 RR 级别下的默认行锁。
>
> 还有意向锁，是表级锁。事务要加行锁之前，先加一个意向锁在表上，这样其他事务想加表锁时，只需要检查有没有意向锁，不用逐行检查。
>
> 从兼容性分，有共享锁 S 和排他锁 X。共享锁是读锁，SELECT ... LOCK IN SHARE MODE。排他锁是写锁，SELECT ... FOR UPDATE 或 UPDATE/DELETE。S 和 S 兼容，S 和 X 互斥，X 和 X 互斥。

### Q26：redo log 和 binlog 的区别？

> redo log 是 InnoDB 引擎层的日志，binlog 是 Server 层的日志。
>
> redo log 是物理日志，记录的是在某页某偏移量做了什么修改。它的作用是 crash-safe，也就是数据库宕机重启后能恢复数据。redo log 是循环写，写满了就刷盘。
>
> binlog 是逻辑日志，记录的是 SQL 语句或行变化。它的作用是主从复制和数据恢复。binlog 是追加写，不会覆盖。
>
> 两个日志的写入用的是两阶段提交。先写 redo log，标记为 prepare 状态。然后写 binlog。最后把 redo log 标记为 commit 状态。这样做的目的是保证两个日志的一致性。如果写完 binlog 后崩溃，恢复时发现 redo log 是 prepare 状态，就检查 binlog 有没有完整的对应记录，有就提交，没有就回滚。

## 第六部分：Spring

### Q27：说一下 Spring IoC

> IoC 是控制反转，核心思想是把对象的创建和依赖关系的管理交给 Spring 容器来做，而不是程序员手动 new。以前是对象主动去依赖其他对象，现在是容器把依赖注入进来，所以控制权反转了。
>
> 实现上，Spring 维护一个 BeanFactory，里面是一个 Map，存了所有 Bean 的定义和实例。通过反射来创建对象。当你需要某个 Bean 时，容器帮你创建并注入它的依赖。
>
> Bean 的生命周期大概是这样的：先实例化，通过反射调用构造方法创建对象。然后属性注入，把依赖的 Bean 注入进来。然后执行各种 Aware 接口的回调，比如 BeanNameAware、BeanFactoryAware。然后执行 BeanPostProcessor 的前置处理。然后初始化，包括 @PostConstruct、InitializingBean 的 afterPropertiesSet、init-method。然后 BeanPostProcessor 的后置处理，这里可能会生成代理对象（AOP）。最后 Bean 可以使用了。销毁的时候执行 @PreDestroy、DisposableBean 的 destroy、destroy-method。

### Q28：说一下 Spring AOP

> AOP 是面向切面编程，把横切逻辑从业务代码中抽离出来。比如日志、事务、权限这些每个方法都需要的逻辑，不用每个方法都写一遍，而是通过 AOP 统一处理。
>
> 底层实现是动态代理。如果目标类实现了接口，就用 JDK 动态代理，通过 Proxy.newProxyInstance 创建代理对象。如果没有实现接口，就用 CGLIB，通过生成目标类的子类来创建代理对象。Spring Boot 2.0 之后默认用 CGLIB。
>
> AOP 有 5 种通知。@Before 在方法执行前。@After 在方法执行后，无论成功失败。@Around 环绕通知，可以控制方法是否执行、修改参数和返回值。@AfterReturning 在方法正常返回后。@AfterThrowing 在方法抛异常后。
>
> 我项目里主要用 AOP 做了日志切面，记录接口的请求参数、响应结果和耗时。还有 @Transactional 其实也是基于 AOP 实现的，Spring 在方法执行前开启事务，正常返回就提交，抛异常就回滚。

### Q29：@Transactional 失效的场景？

> 第一个，方法不是 public 的。Spring 通过动态代理来加事务，默认只对 public 方法生效。因为非 public 方法在代理类中不可见。
>
> 第二个，自调用。就是同一个类里 A 方法调用了 B 方法，B 方法上有 @Transactional。但因为是 this 调用，没有走代理对象，所以事务不生效。解决方法是把 B 方法拆到另一个类里，或者注入自己再调用。
>
> 第三个，异常被 catch 吞掉了。如果在方法里 try-catch 了异常但没有 throw 出去，Spring 认为方法正常执行了，不会回滚。
>
> 第四个，抛出了 checked exception。@Transactional 默认只回滚 RuntimeException 和 Error。如果要回滚所有异常，需要加 rollbackFor = Exception.class。
>
> 第五个，类或方法是 final 的。CGLIB 通过生成子类来创建代理，final 类不能被继承，final 方法不能被重写，所以代理失效。

### Q30：Spring Boot 自动装配原理？

> @SpringBootApplication 注解是一个组合注解，包含 @SpringBootConfiguration、@EnableAutoConfiguration 和 @ComponentScan。
>
> @EnableAutoConfiguration 是自动装配的关键。它通过 @Import 导入了 AutoConfigurationImportSelector。这个类会读取 META-INF/spring.factories 文件，这个文件里配置了很多自动配置类的全限定名。Spring Boot 启动时会把这些配置类加载进来。
>
> 但不是所有的配置类都会生效。每个配置类上都有 @Conditional 条件注解，比如 @ConditionalOnClass 表示 classpath 里有某个类才生效，@ConditionalOnMissingBean 表示容器里没有某个 Bean 才生效。这样就能根据你引入的依赖来自动配置。
>
> 比如你引入了 spring-boot-starter-web，它里面有 Tomcat 和 Spring MVC 的依赖，对应的自动配置类条件满足，就会自动配置 Tomcat 和 DispatcherServlet。你不需要写任何配置文件，开箱即用。

## 第七部分：Redis

### Q31：缓存穿透、雪崩、击穿怎么解决？

> 缓存穿透是查一个数据库和缓存都不存在的数据，每次请求都打到数据库。解决方法有两种，一是缓存空值，查到数据库没有就缓存一个 null 值，设置短过期时间。二是用布隆过滤器，在缓存之前加一层判断，布隆过滤器说不存在的数据直接返回，不查缓存也不查数据库。
>
> 缓存雪崩是大量 key 同时过期，导致大量请求同时打到数据库。解决方法是给过期时间加随机值，避免同时过期。另外可以加多级缓存，比如本地缓存 Caffeine 加 Redis。还可以做熔断降级，数据库扛不住时直接返回兜底数据。
>
> 缓存击穿是热点 key 过期的瞬间，大量并发请求同时来查，都打到数据库。解决方法一是用分布式锁，只让一个线程去查数据库并回写缓存，其他线程等待或返回旧值。二是设置逻辑过期，不设 TTL，在 value 里存一个过期时间，后台异步刷新。
>
> 这三个问题的本质都是缓存不可用导致请求打到数据库，区别在于穿透是数据不存在，雪崩是大量 key 过期，击穿是单个热点 key 过期。

### Q32：Redis 分布式锁怎么实现？

> 最简单的实现是用 SETNX 命令，SET key value NX EX 30，这个命令是原子的，NX 表示 key 不存在才设置，EX 30 表示 30 秒过期。加锁成功就返回 OK，失败返回 nil。
>
> 但这个方案有锁过期的问题。如果业务执行时间超过锁的过期时间，锁会被自动释放，其他线程就能拿到锁，导致并发问题。解决方法是 Redisson 的看门狗机制，它会在一个后台线程中定期检查当前线程是否还持有锁，如果还在就续期。
>
> Redisson 的分布式锁还支持可重入。它在 value 里存了线程 ID 和重入次数，同一个线程多次加锁只是次数加一，不会死锁。
>
> 如果是 Redis 单节点，宕机了锁就没了。可以用 Red Lock 算法，向多个 Redis 节点同时加锁，超过半数成功就算加锁成功。但 Red Lock 也有争议，比如网络分区时可能出问题。生产环境如果对可靠性要求很高，建议用 Zookeeper 或 etcd 来做分布式锁。

### Q33：Redis 为什么这么快？

> 主要有四个原因。第一，Redis 完全基于内存操作，内存的读写速度远超磁盘。这是最根本的原因。
>
> 第二，Redis 核心是单线程的，避免了多线程的上下文切换和锁竞争。虽然单线程看起来慢，但内存操作本身极快，单线程也能处理十万级别的 QPS。
>
> 第三，Redis 使用了 IO 多路复用，epoll 模型。单线程能同时处理大量客户端连接，select 调用一次就能知道哪些 fd 有事件，不需要每个连接轮询。
>
> 第四，Redis 的数据结构设计得很高效。比如 String 用了 SDS，预分配空间减少内存重分配次数。ZSet 用了跳表，查找和范围查询都是 O(log n)。小数据量用压缩列表，内存紧凑。
>
> Redis 6.0 之后引入了 IO 多线程，但只是用在网络读写和协议解析上，命令执行还是单线程。所以本质上还是单线程模型。

## 第八部分：项目场景题

### Q34：如果让你重新设计你的选课系统，你会怎么改？

> 如果重新设计，我会从几个方面优化。
>
> 第一，认证方式从 Session 改成 JWT。现在用 Session 导致微服务之间不能共享登录状态，如果改成 JWT，Token 自包含用户信息，每个服务自己解析就行，不需要共享 Session。
>
> 第二，加 Redis 缓存。热点课程信息、已选人数这些高频读的数据可以放 Redis，减少数据库压力。选课的时候先用 Redis DECR 原子操作预扣库存，成功再写数据库，失败直接返回。
>
> 第三，引入消息队列。选课高峰期可以用 RabbitMQ 或 Kafka 削峰，用户的选课请求先入队列，后端慢慢消费写数据库。
>
> 第四，统一 ORM。现在 MyBatis-Plus 和 JPA 混用了，应该统一成 MyBatis-Plus，因为它的 QueryWrapper 更灵活，适合复杂查询。
>
> 第五，加链路追踪和日志收集。微服务调用链路复杂，出问题很难排查。可以用 SkyWalking 做链路追踪，ELK 做日志收集。
>
> 第六，加单元测试。现在项目几乎没有测试，应该补上 Service 层的测试，保证代码质量。
>
> 第七，Docker 化部署，配合 CI/CD 实现自动化部署。

### Q35：你的项目还有什么不足？

> 我觉得有几个比较明显的问题。
>
> 第一个是双 ORM 混用。我在 StudentServiceImpl 里用了 MyBatis-Plus 的 QueryWrapper，但在 CourseServiceImpl 里用了 JPA Repository。这两个 ORM 的设计理念和 API 完全不同，混用会让代码风格不统一，维护成本高。应该统一成 MyBatis-Plus。
>
> 第二个是内存分页。在 UserServiceImpl 里，因为用户数据分散在 student、teacher、admin 三张表里，我把三张表的数据全查出来在内存里合并排序再分页。这个方案在数据量大的时候会有性能问题和内存风险。应该改成数据库层面的分页，或者用 Elasticsearch 做聚合。
>
> 第三个是有硬编码。管理员登录有一个 admin/admin123 的兜底逻辑，还有教师密码做了特殊哈希值的硬编码匹配。这些都是临时方案，应该用数据库统一管理。
>
> 第四个是微服务路由没有真正启用。我搭好了 Eureka 和 Gateway，5 个微服务模块也有骨架，但因为 Session 跨服务的问题，Gateway 实际配置的是全转发到 web-service。这是一个待解决的问题。
>
> 第五个是缺少测试。整个项目只有启动测试，没有 Service 层的单元测试和 Controller 层的集成测试。
>
> 我觉得主动暴露问题并给出改进方向，比假装完美更重要。

### Q36：你说用了 BCrypt 加密密码，为什么不用 MD5？

> MD5 有几个问题。第一，MD5 虽然不可逆，但可以通过彩虹表反查。彩虹表是预先算好的哈希值对照表，对常见的密码可以直接查到原文。
>
> 第二，MD5 计算太快了。这对密码加密反而是缺点，因为攻击者可以快速暴力破解，每秒可以算几亿次。
>
> 第三，MD5 不加 salt 的话，相同密码的哈希值相同，攻击者只要算一次就能破解所有相同密码的账户。即使加了 salt，因为计算快，还是不够安全。
>
> BCrypt 解决了这些问题。第一，BCrypt 自带 salt，每次加密结果都不同，即使两个用户密码相同，哈希值也不同。第二，BCrypt 有一个 cost 参数，控制计算复杂度，可以随着硬件性能提升而调大，让暴力破解越来越慢。第三，BCrypt 计算本来就慢，每秒只能算几千次，大大增加了暴力破解的成本。
>
> 在 Spring Security 里，用 BCryptPasswordEncoder 一行代码就能搞定。我在注册时加密，登录时用 matches 方法验证，非常方便。

### Q37：你的 AI Agent 项目是怎么实现工具调用的？

> 大致流程是这样的。首先我定义了一个 Tool 接口，每个接口有 name、description 和 execute 三个方法。description 会告诉 LLM 这个工具能做什么、接受什么参数。
>
> 我实现了几个工具，比如天气查询、待办管理、翻译。每个工具就是 Tool 接口的一个实现类。
>
> 调用流程是：用户输入文字 → 我把用户输入和所有工具的描述组装成 prompt 发给 LLM → LLM 返回一个 tool_calls 结构，里面包含工具名和参数 → 我解析这个返回，用反射找到对应的 Java 方法并调用 → 把工具执行结果回传给 LLM → LLM 根据结果生成自然语言回复返回给用户。
>
> 这个流程是可以循环的，LLM 可以连续调用多个工具，直到它认为可以给用户回复了。
>
> 前端我用 SSE 实现了流式输出，就是打字机效果。后端用 SseEmitter，每次 LLM 返回一个 token 就推给前端，前端用 ReadableStream 实时渲染。
>
> 遇到的一个问题是上下文长度限制。LLM 的上下文窗口是 8K token，多轮对话很容易超。我做了会话摘要，当对话超过一定长度时，把前面的对话总结成一段摘要，压缩上下文。这样可以在 8K 限制下支持最多 30 轮对话。

### Q38：你了解的设计模式有哪些？在项目中怎么用的？

> 我比较常用的有几种。
>
> 策略模式，用在成绩计算上。我定义了一个 ScoreStrategy 接口，不同评分方案是实现类。比如默认方案是平时 40% + 实验 20% + 考试 40%，以后如果需要加其他方案，只需要新增一个实现类，在工厂里注册一下就行，不用改原有代码，符合开闭原则。
>
> 工厂模式，在 Service 层根据用户角色创建不同的处理器。比如登录的时候，根据 role 参数决定走学生登录、教师登录还是管理员登录的逻辑，用一个工厂方法来创建对应的 Service 实现。
>
> 代理模式，这是 Spring AOP 的底层。我的日志切面就是通过动态代理在方法前后插入日志逻辑，不需要修改业务代码。
>
> 单例模式，Spring 的 Bean 默认都是单例的，整个容器中只有一个实例。
>
> 模板方法模式，我的 Controller 公共流程其实是一个模板。都是接收参数、调用 Service、封装 Result 返回，这个流程是固定的，变化的只是具体调哪个 Service 方法。
>
> 观察者模式，Spring 的事件机制。ApplicationEventPublisher 发事件，@EventListener 监听事件，实现解耦。比如选课成功后可以发一个事件，通知统计模块更新人数，不直接调用统计接口。

### Q39：你是怎么使用 AI 工具辅助开发的？

> 我平时用 Trae 和 Cursor 这两个 AI IDE 辅助开发。主要用在几个方面。
>
> 第一是代码生成。比如我写了一个 Controller，让它帮我生成对应的 Service 接口和实现类的骨架，节省重复劳动。
>
> 第二是 debug。遇到报错把错误信息贴给 AI，它帮我分析可能的原因。上次遇到一个 MyBatis-Plus 的分页不生效问题，AI 提醒我没加 PaginationInnerInterceptor 配置，一下就解决了。
>
> 第三是学习新技术。比如我学 Spring Cloud 的时候，先让 AI 给我讲整体架构，再深入到每个组件。
>
> 第四是代码 review。写完一段逻辑让 AI 检查有没有问题，有没有安全隐患。
>
> 但我不会完全依赖 AI。AI 写的代码我会自己审查逻辑，确保理解每一行的作用。AI 给的方案我也会思考有没有更好的实现方式。我觉得 AI 工具的价值在于提高效率，而不是替代思考。

### Q40：什么是 Spring 的循环依赖？怎么解决的？

> 循环依赖就是 A 依赖 B，B 又依赖 A。Spring 只能解决 setter 注入的单例 Bean 之间的循环依赖，构造器注入的循环依赖解决不了。
>
> 解决方法是用三级缓存。第一级 singletonObjects 存完整的 Bean，第二级 earlySingletonObjects 存半成品 Bean，第三级 singletonFactories 存 ObjectFactory。
>
> 流程是这样的：创建 A，先实例化 A，把 A 的 ObjectFactory 放到第三级缓存。然后 A 要注入 B，去创建 B，实例化 B 后把 B 的 ObjectFactory 放到第三级。B 要注入 A，从第三级缓存拿到 A 的 ObjectFactory，调用它得到 A 的早期引用（可能是代理对象），放到第二级。B 拿到 A 的引用，B 创建完成放到第一级。A 继续注入 B，从第一级拿到 B，A 也创建完成。
>
> 为什么要用第三级 ObjectFactory 而不直接存半成品？因为如果 A 需要 AOP 代理，需要通过 ObjectFactory 来创建代理对象，不能直接存原始对象。
>
> Spring 4.3 之后引入 @Lazy 注解可以解决构造器循环依赖，原理是注入一个代理对象，真正使用时才创建。

### Q41：说一下 Spring 事务传播机制

> 事务传播机制定义了一个事务方法被另一个事务方法调用时，事务怎么传播。一共有 7 种。
>
> 最常用的是 REQUIRED，这是默认的。如果当前有事务就加入，没有就新建。比如方法 A 调用方法 B，A 有事务，B 就加入 A 的事务，一起提交或回滚。
>
> REQUIRES_NEW，总是新建事务，把当前事务挂起。A 调用 B，B 会新开一个事务，A 的事务暂停。B 提交或回滚不影响 A，A 恢复后继续自己的事务。适合日志记录这种不管业务成功失败都要记录的场景。
>
> NESTED，嵌套事务。基于 savepoint 实现，外层回滚则内层也回滚，但内层回滚不影响外层。
>
> 其他几种：SUPPORTS 有就加入没有就非事务运行。NOT_SUPPORTED 非事务运行。MANDATORY 必须有事务否则抛异常。NEVER 不能有事务否则抛异常。
>
> 在我的项目里，选课操作用 REQUIRED，选课成功后更新统计也是 REQUIRED，保证一起成功失败。退课和候补提升也在同一个事务里。

### Q42：MySQL 索引怎么优化？

> 我一般从几个方面来做。
>
> 首先是用 EXPLAIN 看执行计划。重点看 type 字段，如果是 ALL 说明全表扫描，需要加索引。如果是 index 说明扫描了整个索引树，也不太好。理想是 ref 或 range。还要看 Extra 字段，Using filesort 说明用了文件排序，需要优化。Using temporary 说明用了临时表，也需要优化。
>
> 然后是建索引的策略。第一，优先在 WHERE、JOIN、ORDER BY、GROUP BY 涉及的列上建索引。第二，区分度高的列适合建索引，比如手机号适合，性别不适合。第三，联合索引要遵循最左前缀原则，把区分度高的列放前面。第四，尽量用覆盖索引，把查询字段都包含在索引里，避免回表。
>
> 对于慢查询，常见的优化有：避免 SELECT * 只查需要的列；分页优化，大数据量分页用游标分页代替 LIMIT offset；JOIN 不超过 3 张表，JOIN 字段必须有索引；子查询改写成 JOIN；避免在索引列上做函数操作。
>
> 在我的选课系统里，选课记录表我对 (student_id, status) 建了联合索引，因为"查询某学生的已选课程"是最高频的查询。

### Q43：Redis 怎么做缓存一致性？

> 缓存和数据库一致性问题，核心是先更新数据库还是先更新缓存的问题。
>
> 常见的有几种策略。第一种是 Cache Aside，读的时候先读缓存，没有就读数据库然后写缓存。写的时候先更新数据库再删缓存。这是最常用的方案。
>
> 为什么是删缓存而不是更新缓存？因为多个并发写可能导致缓存存的是旧数据。而且有些缓存值计算复杂，更新缓存可能浪费时间，如果这个数据很少被读，就没必要更新。
>
> 但 Cache Aside 也有问题。先更新数据库再删缓存，如果删缓存失败，缓存里就是旧数据。解决方法是可以用消息队列重试删除，或者设置过期时间兜底。
>
> 另外一种方案是延迟双删。先删缓存，再更新数据库，延迟一段时间后再删一次缓存。第二次删是为了在更新数据库期间其他线程读到的旧数据被清除。
>
> 对一致性要求很高的场景，可以用 Canal 监听 binlog，异步更新缓存，这样业务代码不需要管缓存逻辑。

### Q44：分布式事务怎么处理？

> 分布式事务是一个复杂问题，有几种常见方案。
>
> 第一种是 2PC，两阶段提交。有一个协调者，第一阶段让所有参与者准备，第二阶段统一提交或回滚。问题是同步阻塞，协调者宕机会阻塞。MySQL 的 XA 协议就是 2PC。
>
> 第二种是 TCC，Try-Confirm-Cancel。Try 阶段预留资源，Confirm 阶段确认，Cancel 阶段回滚。需要业务代码配合，侵入性大。比如选课系统，Try 阶段先预扣容量，Confirm 阶段正式写入，Cancel 阶段释放容量。
>
> 第三种是本地消息表。在本地事务里写业务数据和消息表，然后有个定时任务扫描消息表，发消息到 MQ。下游消费消息处理，成功后回报。这种方式保证了最终一致性。
>
> 第四种是 Seata。阿里开源的分布式事务框架，支持 AT、TCC、SAGA、XA 四种模式。AT 模式最常用，业务无侵入，原理是生成反向 SQL 自动回滚。
>
> 在我的选课系统里，因为目前还是单体运行，没有真正的分布式事务问题。但如果微服务真正拆开后，选课需要同时操作选课服务和课程服务，就需要用 Seata 或本地消息表来处理。
